# SC — Segurança (Java)

Padrões do time para a stack Java nesta família de slots, de propriedade do `prime-core/coding-standards`. Lidos junto com o índice, `references/defaults-java.md`, que guarda como ler as marcas (Spring), (Boot 4) e (Java 21+), a Plataforma e a Toolchain do time. As definições dos slots estão no arquivo de mesmo nome em `references/convention-slots/`.

- **CS-SC-1** — A autorização é imposta no serviço de aplicação, em nível de método (`@PreAuthorize` com `@EnableMethodSecurity`, ou verificação explícita) **(Spring)**. A configuração de segurança, no DSL de lambdas do Spring Security 7, nega por padrão: toda rota não declarada é negada (`anyRequest().denyAll()` depois das regras explícitas). Uma operação sobre um recurso por identificador verifica que o recurso pertence ao chamador — com a consulta já restrita ao titular, nunca filtrando depois de carregar. Erro na decisão de autorização nega. Uma verificação feita só no controller é insuficiente; uma verificação feita só no cliente não é uma verificação. *Razão:* controle de acesso quebrado é o risco número um da OWASP, e a forma mais comum é o acesso a recurso alheio por identificador. *Verificação:* testes de autorização negativa por endpoint novo — sem permissão e sobre recurso de outro titular; revisão.
- **CS-SC-2** — Bean Validation em todo DTO de fronteira, com semântica de allowlist. Consultas parametrizadas — nunca concatenação em JPQL, SQL nativo ou Criteria. A entrada externa nunca chega a um caminho de arquivo, a um comando ou a um desserializador sem neutralização. Saída codificada pelo contexto: templates com escape automático; valores em log só por parâmetro do SLF4J, sem quebras de linha vindas da entrada. *Razão:* quase toda injeção é dado que cruzou para código sem ser neutralizado. *Verificação:* Semgrep, SpotBugs com find-sec-bugs, SAST no pipeline.
- **CS-SC-3** — Nenhuma credencial em `application.yml`, em arquivo de propriedades, em fixture de teste ou no controle de versão. Resolvidas do cofre do projeto (Spring Cloud Vault ou o gerenciador de segredos da nuvem) ou, no Kubernetes, montadas como arquivos e importadas por `spring.config.import=configtree:` **(Spring)**; rotacionáveis sem rebuild. *Razão:* o histórico do Git é permanente. *Verificação:* gitleaks no pre-commit e no pipeline.
- **CS-SC-4** — Senha nova com Argon2id nos parâmetros mínimos da OWASP — 19 MiB de memória, 2 iterações, paralelismo 1: `new Argon2PasswordEncoder(16, 32, 1, 19456, 2)` —, registrado num `DelegatingPasswordEncoder` com o identificador `argon2` **(Spring)**. Hashes bcrypt existentes continuam válidos pelo mesmo encoder e são regravados em Argon2id no login (`UserDetailsPasswordService`). Tokens JWT são validados pelo OAuth2 Resource Server do Spring Security e emitidos pelo provedor de identidade do projeto ou pelo Spring Authorization Server **(Spring)** — nunca montados nem conferidos à mão. Nenhum algoritmo artesanal, nenhum `MessageDigest` como hash de senha, nenhum `Random` onde `SecureRandom` é exigido. *Razão:* criptografia própria falha de formas que nenhum teste funcional mostra, e um parâmetro fraco de hash só aparece no dia do vazamento. *Verificação:* SpotBugs com find-sec-bugs; regra Semgrep.
- **CS-SC-5** — OWASP ASVS 5.0 Nível 2 como conjunto de controles de referência; Nível 3 nas áreas `crítica` quando o modelo de ameaças do projeto o pede. *Razão:* um padrão externo mantido por especialistas em vez de uma lista reescrita e envelhecida. *Verificação:* revisão contra os controles aplicáveis.
- **CS-SC-6** — Quatro classes de dado protegido:
  - `credencial` — senha, token, chave;
  - `sensível` — dado pessoal sensível conforme a LGPD (art. 5º, II): saúde, biometria, origem racial ou étnica e afins;
  - `financeiro` — número de cartão, conta, saldo;
  - `pessoal` — o que identifica alguém: nome, CPF, e-mail, telefone, endereço.

  O campo usa um tipo de valor da classe (`Cpf`, `Email`, `NumeroCartao`) com `toString()` mascarado. `credencial` nunca é registrada, retornada ou guardada em claro. `sensível` e `financeiro` são mascarados em toda resposta que não precise do valor completo, e seu acesso é auditado (`CS-OB-5`) nas áreas `crítica`. `pessoal` fica fora dos logs e é exposto só onde a finalidade pede. A retenção de cada classe é declarada pelo projeto. *Razão:* sem classificação, cada dev decide sozinho o que é sensível — e decide diferente. *Verificação:* revisão; teste do `toString()` mascarado.
