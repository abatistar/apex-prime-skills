# AR — Arquitetura e dependências (Java)

Padrões do time para a stack Java nesta família de slots, de propriedade do `prime-core/coding-standards`. Lidos junto com o índice, `references/defaults-java.md`, que guarda como ler as marcas (Spring), (Boot 4) e (Java 21+), a Plataforma e a Toolchain do time. As definições dos slots estão no arquivo de mesmo nome em `references/convention-slots/`.

- **CS-AR-1** — Arquitetura hexagonal (portas e adaptadores). Cada microsserviço tem estes elementos, e as dependências apontam para dentro:
  - **domínio** — o modelo e as regras de negócio; não depende de nenhum outro elemento;
  - **aplicação** — os casos de uso: as portas de entrada, as portas de saída e os serviços que implementam as portas de entrada; depende só do domínio;
  - **adaptadores de entrada** (HTTP, mensageria, agendamento) e **adaptadores de saída** (persistência, clientes de outros serviços, publicação de eventos) — dependem da aplicação e do domínio, nunca uns dos outros;
  - **montagem** — liga cada porta de saída ao adaptador que a implementa; o único elemento que conhece todos os outros.

  O pacote que representa cada elemento é decisão do projeto, declarada na seção Estrutura da configuração; este padrão não fixa nomes de pacote. *Razão:* o núcleo fica testável sem infraestrutura, e cada tecnologia fica trocável atrás de uma porta. *Verificação:* teste ArchUnit com `Architectures.onionArchitecture()`, que quebra o build, alimentado pelos pacotes que a Estrutura declara para cada elemento. Uma Estrutura que não declara o pacote de um elemento é uma lacuna a reportar: sem ela, o teste não tem o que verificar.
- **CS-AR-2** — As decisões de negócio vivem no domínio, cada regra num único método ou tipo que todo ponto que precisa dela chama. O serviço de aplicação orquestra o caso de uso — carrega pelas portas de saída, chama o domínio, grava, publica — e não decide regra de negócio. Um adaptador de entrada traduz e chama a porta de entrada; um adaptador de saída implementa uma porta de saída. Uma condicional que expressa uma regra de negócio num adaptador, num serviço de aplicação ou numa consulta além de filtrar é um defeito. *Razão:* a regra fora do domínio é a que acaba duplicada e divergente. *Verificação:* revisão; ArchUnit para os imports.
- **CS-AR-3** — Cada tipo de tecnologia fica no adaptador que o usa. A entidade JPA (`*JpaEntity`) vive no adaptador de persistência e é mapeada para o modelo de domínio ali; o DTO de requisição e resposta vive no adaptador HTTP de entrada e é mapeado para o comando da porta de entrada ali; o payload de mensagem vive no adaptador de mensageria. Nenhum import de `jakarta.persistence`, de tipos web ou de mensageria no domínio e na aplicação; no domínio, nenhum import de `org.springframework`; na aplicação, só as anotações de transação e de estereótipo do Spring. *Razão:* tipo de tecnologia no núcleo amarra o domínio à infraestrutura e faz da tabela ou do payload o contrato. *Verificação:* ArchUnit.
- **CS-AR-4** — Um microsserviço é um contexto delimitado: os pacotes se organizam primeiro pelos elementos do hexágono, não por feature. Quando o serviço tem mais de um agregado, o pacote de cada elemento se subdivide por agregado. Os nomes concretos ficam na Estrutura da configuração. O empacotamento em camadas técnicas (controller → service → repository) é a forma legada e não é estendido. Um serviço que precisa de módulos internos com fronteiras próprias é candidato a divisão — decisão de ADR. *Razão:* a mesma forma em todo serviço, para que qualquer pessoa do time encontre a porta, o caso de uso e o adaptador sem procurar. *Verificação:* ArchUnit.
- **CS-AR-5** — Dentro do serviço, o caminho é sempre o mesmo: adaptador de entrada → porta de entrada → serviço de aplicação → portas de saída. Entre serviços, evento assíncrono pelo broker para o que não precisa de resposta imediata, e HTTP síncrono, por cliente de serviço HTTP, só quando a operação precisa da resposta para concluir. Nunca o banco de outro serviço, nem para leitura. Qualquer outra coisa é justificada na ITS. *Razão:* cada chamada síncrona entre serviços soma a indisponibilidade do outro à sua, e banco compartilhado é acoplamento invisível entre serviços (`QM-CC-1`). *Verificação:* revisão; ArchUnit para dependências de adaptador.
