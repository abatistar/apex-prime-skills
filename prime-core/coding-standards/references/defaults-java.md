# Padrões do Time — Java

Valores padrão de slots para a stack Java do time, de propriedade do `prime-core/coding-standards`. Aplicados quando o `docs/prime-config.md` nada declara para o slot; qualquer valor que o projeto declare vence. Estes padrões são versionados pela release do Apex Prime que os traz: o projeto fixa na configuração a release que segue, e uma release nova só o alcança quando ele a adota (SKILL.md, Padrões do time). As definições dos slots e as classes de aplicação vivem em `convention-slots.md` — este arquivo apenas fornece respostas.

Cada entrada traz o valor, a **razão** — a falha que ele evita — e a **verificação** concreta. Os exemplos canônicos são do projeto, declarados na configuração: um padrão do time não conhece o código de ninguém.

Uma marca **(Spring)** delimita o mecanismo que ela acompanha, nunca a entrada que a carrega. `@RestControllerAdvice`, `@Transactional`, `@PreAuthorize`, `spring.jpa.open-in-view` e afins são como um projeto Spring Boot atende ao slot; um projeto em outro framework substitui por um mecanismo equivalente e mantém tudo o mais que a entrada diz — a camada a que a decisão pertence, as proibições e as alternativas não Spring nomeadas ao lado. Nenhuma entrada marcada perde sua substância sob essa substituição, de modo que nenhuma delas manda um projeto declarar o slot do zero na sua configuração. Um tipo Spring citado *sem* a marca é ilustração, não uma dependência: a regra ao redor dele vale como escrita.

Uma marca **(Boot 4)** ou **(Java 21+)** delimita um mecanismo que só existe a partir dessa versão. Abaixo dela, vale a alternativa nomeada na mesma entrada, e a regra ao redor continua valendo.

## Plataforma

- **Referência para projeto novo:** Java 25, a versão LTS corrente, e Spring Boot 4 — com Spring Framework 7, Spring Security 7, Jakarta EE 11, Hibernate 7 e Jackson 3. O time segue versões LTS do Java; uma versão intermediária só entra quando a Stack do projeto a declara.
- **Mínimo:** Java 17, o mínimo do Spring Boot 4. Um recurso de linguagem ou de framework acima da versão que a Stack do projeto declara nunca é usado nem planejado.
- **Spring Boot 3:** fora do suporte de código aberto desde 30 de junho de 2026. Um projeto nele trata a subida para o Boot 4 como migração declarada; as receitas do OpenRewrite executam a parte mecânica (Boot, Jackson 2 → 3, anotações de teste).
- **Threads virtuais (Java 21+):** o modelo padrão para I/O bloqueante, com `spring.threads.virtual.enabled=true` **(Spring)**. Sem um pool de threads limitando o paralelismo, o limite passa a ser declarado onde o recurso é escasso: o pool de conexões do banco tem tamanho explícito, e uma dependência que não aguenta carga recebe limite de concorrência (`CS-RS-2`). Até o Java 23, um bloco `synchronized` em volta de I/O prende a thread portadora; a partir do Java 24 não prende mais.

## AR — Arquitetura e dependências

- **CS-AR-1** — Arquitetura hexagonal (portas e adaptadores). Cada microsserviço tem quatro áreas de pacote, e as dependências apontam para dentro:
  - `domain` — o modelo e as regras de negócio; não depende de nada fora dele;
  - `application` — os casos de uso: as portas de entrada (`port.in`), as portas de saída (`port.out`) e os serviços que implementam as portas de entrada; depende só de `domain`;
  - `adapter.in.<tipo>` e `adapter.out.<tipo>` — os adaptadores: de entrada (HTTP, mensageria, agendamento) e de saída (persistência, clientes HTTP, publicação de eventos); dependem de `application` e de `domain`, nunca uns dos outros;
  - `config` — monta o hexágono, ligando cada porta de saída ao adaptador que a implementa; o único pacote que conhece todos os outros.

  *Razão:* o núcleo fica testável sem infraestrutura, e cada tecnologia fica trocável atrás de uma porta. *Verificação:* teste ArchUnit com `Architectures.onionArchitecture()` — domínio, serviços de aplicação e cada adaptador declarados pelos pacotes acima —, que quebra o build.
- **CS-AR-2** — As decisões de negócio vivem em `domain`, cada regra num único método ou tipo que todo ponto que precisa dela chama. O serviço de aplicação orquestra o caso de uso — carrega pelas portas de saída, chama o domínio, grava, publica — e não decide regra de negócio. Um adaptador de entrada traduz e chama a porta de entrada; um adaptador de saída implementa uma porta de saída. Uma condicional que expressa uma regra de negócio num adaptador, num serviço de aplicação ou numa consulta além de filtrar é um defeito. *Razão:* a regra fora do domínio é a que acaba duplicada e divergente. *Verificação:* revisão; ArchUnit para os imports.
- **CS-AR-3** — Cada tipo de tecnologia fica no adaptador que o usa. A entidade JPA (`*JpaEntity`) vive em `adapter.out.persistence` e é mapeada para o modelo de domínio ali; o DTO de requisição e resposta vive em `adapter.in.web` e é mapeado para o comando da porta de entrada ali; o payload de mensagem vive no adaptador de mensageria. Nenhum import de `jakarta.persistence`, de tipos web ou de mensageria em `domain` e `application`; em `domain`, nenhum import de `org.springframework`; em `application`, só as anotações de transação e de estereótipo do Spring. *Razão:* tipo de tecnologia no núcleo amarra o domínio à infraestrutura e faz da tabela ou do payload o contrato. *Verificação:* ArchUnit.
- **CS-AR-4** — Um microsserviço é um contexto delimitado: o primeiro nível de pacotes é o hexágono (`domain`, `application`, `adapter`, `config`), não a feature. Quando o serviço tem mais de um agregado, cada área se subdivide por agregado (`domain.order`, `application.order`). O empacotamento em camadas técnicas (`api`, `service`, `persistence`) é a forma legada e não é estendido. Um serviço que precisa de módulos internos com fronteiras próprias é candidato a divisão — decisão de ADR. *Razão:* a mesma forma em todo serviço, para que qualquer pessoa do time encontre a porta, o caso de uso e o adaptador sem procurar. *Verificação:* ArchUnit.
- **CS-AR-5** — Dentro do serviço, o caminho é sempre o mesmo: adaptador de entrada → porta de entrada → serviço de aplicação → portas de saída. Entre serviços, evento assíncrono pelo broker para o que não precisa de resposta imediata, e HTTP síncrono, por cliente de serviço HTTP, só quando a operação precisa da resposta para concluir. Nunca o banco de outro serviço, nem para leitura. Qualquer outra coisa é justificada na ITS. *Razão:* cada chamada síncrona entre serviços soma a indisponibilidade do outro à sua, e banco compartilhado é acoplamento invisível entre serviços (`QM-CC-1`). *Verificação:* revisão; ArchUnit para dependências de adaptador.

## NM — Nomenclatura e estrutura

- **CS-NM-1** — Os nomes dizem a peça do hexágono:
  - porta de entrada: `<Ação>UseCase` (interface), com a entrada num `<Ação>Command` (`record`) — `ConfirmOrderUseCase`, `ConfirmOrderCommand`;
  - serviço de aplicação: `<Ação>Service`, que implementa a porta de entrada;
  - porta de saída: `<Verbo><Objeto>Port` — `LoadOrderPort`, `SaveOrderPort`, `PublishOrderEventPort`;
  - adaptador de entrada: `*Controller` (HTTP), `*Listener` (mensageria), `*Job` (agendamento);
  - adaptador de saída: `*PersistenceAdapter` (implementa as portas de persistência sobre um `*Repository` do Spring Data e as `*JpaEntity`), `*Client` (HTTP, sobre a interface de cliente de serviço HTTP), `*Publisher` (mensageria);
  - de apoio: `*Mapper`, `*Config`, `*Properties`, `*Test`, `*IT`.

  Nenhum `*Manager`, `*Helper`, `*Util` em código novo. *Razão:* cada um desses é um nome para "eu não decidi o que isto é", e o nome da peça diz em que lado do hexágono ela está. *Verificação:* regra de nomenclatura no ArchUnit.
- **CS-NM-2** — `getX()` e `isX()` são puros e baratos: sem I/O, sem mutação, sem evento. Tudo o que alcança armazenamento ou rede é `load*`, `fetch*` ou `find*`; tudo o que muta é um verbo que nomeia o efeito (`confirmOrder`, não `processOrder`). *Razão:* quem chama um `get` não espera uma consulta ao banco num laço. *Verificação:* revisão; regra Semgrep para I/O dentro de `get*`.
- **CS-NM-3** — Um tipo usado por exatamente uma feature vive no pacote dessa feature, nunca num pacote compartilhado. *Razão:* o pacote compartilhado vira depósito do que ninguém quis decidir. *Verificação:* revisão.

## ER — Erros

- **CS-ER-1** — Situações de domínio esperadas são subclasses tipadas de `BusinessException` (não verificada). Invariantes violados usam `IllegalStateException` / `IllegalArgumentException` e nunca são capturados como fluxo de controle. Sem exceções verificadas em código novo. *Razão:* o tipo diz a quem lê se a falha é do negócio ou do código. *Verificação:* revisão.
- **CS-ER-2** — Toda subclasse de `BusinessException` carrega um código de erro estável. Uma nova categoria é uma nova subclasse mais um código, nunca uma mensagem em texto interpretada pelo chamador. *Razão:* o chamador decide pelo código, que não muda quando a mensagem muda. *Verificação:* revisão.
- **CS-ER-3** — Os erros são traduzidos nas bordas do hexágono, uma vez em cada. O adaptador de saída traduz a exceção da tecnologia que usa (`DataAccessException`, o erro HTTP de outro serviço, a falha do broker) para uma exceção da porta, com a causa; nenhuma exceção de infraestrutura chega a `application` ou `domain`. O adaptador de entrada traduz para quem chama — no HTTP, num `@RestControllerAdvice` que estende `ResponseEntityExceptionHandler` **(Spring)**. Serviço de aplicação e domínio propagam. Nenhum `try/catch` cujo único ato seja registrar em log e relançar. *Razão:* exceção de infraestrutura no núcleo amarra o domínio à tecnologia, e registrar e relançar em cada camada multiplica a mesma falha no log. *Verificação:* ArchUnit para tipos de exceção de infraestrutura no núcleo; revisão; regra Semgrep para catch que só registra e relança.
- **CS-ER-4** — Para fora: Problem Details (RFC 9457) via `ProblemDetail` **(Spring)**, com o código de erro estável num membro de extensão `code` e uma mensagem segura — sem stack trace, sem identificador interno, sem SQL. `spring.mvc.problemdetails.enabled=true`, para que as exceções do próprio framework saiam no mesmo formato. Para dentro: a exceção completa com a causa, registrada uma vez na fronteira que a traduz. *Razão:* um formato padrão para quem chama; todo o detalhe só para quem opera. *Verificação:* teste de integração do advice para cada categoria de erro.
- **CS-ER-5** — Sempre `throw new SomethingException(message, cause)`. Nunca `new RuntimeException(e.getMessage())`. *Razão:* descartar a causa apaga a cadeia que o diagnóstico precisa. *Verificação:* Error Prone; regra Semgrep.
- **CS-ER-6** — Proibido: `catch` vazio; `catch (Exception e)` fora do advice de fronteira; `catch` que retorna `null` ou um valor padrão no lugar de sinalizar; resultados de `Future`/`CompletableFuture` ignorados. *Razão:* cada uma dessas formas transforma uma falha em sucesso aparente. *Verificação:* Error Prone, SpotBugs, Semgrep.
- **CS-ER-7** — Nas áreas `current`, cada pacote declara `@NullMarked` (JSpecify) no `package-info.java`, e o NullAway roda no build em modo JSpecify (`-XepOpt:NullAway:JSpecifyMode=true`, `-XepOpt:NullAway:OnlyNullMarked=true`): o tipo diz se um valor pode ser nulo, com `@Nullable`. `Optional` só como retorno de uma consulta que pode não encontrar — nunca em campo, parâmetro ou elemento de coleção. Uma coleção é vazia, nunca nula. *Razão:* a nulidade declarada no tipo é verificada pelo compilador em vez de descoberta em produção; o Spring Framework 7 e o JUnit 6 publicam suas APIs com as mesmas anotações. *Verificação:* NullAway no build para os pacotes marcados.

## OB — Observabilidade

- **CS-OB-1** — Somente SLF4J, mensagens parametrizadas (`log.info("order confirmed {}", id)`) — nunca concatenação. Saída estruturada pelo suporte nativo do Spring Boot: `logging.structured.format.console=ecs` (ou `logstash`, conforme o coletor do projeto) **(Spring)**, sem encoder montado à mão. `ERROR` = precisa de um humano esta noite; `WARN` = degradado mas tratado; `INFO` = aconteceu um evento de negócio; `DEBUG` = diagnóstico, desligado em produção. *Razão:* nível com significado e formato padrão são o que torna alerta e busca confiáveis. *Verificação:* regra Semgrep para concatenação em log; revisão dos níveis.
- **CS-OB-2** — W3C Trace Context (`traceparent`) em toda requisição recebida, mensagem consumida e chamada de saída; `traceId` e `spanId` no MDC de cada linha. Micrometer Tracing com OpenTelemetry e exportação OTLP — `spring-boot-starter-opentelemetry` **(Boot 4)** **(Spring)**. *Razão:* um formato só, para que uma requisição seja seguida através de todos os serviços. *Verificação:* teste de integração que confere o cabeçalho propagado numa chamada de saída.
- **CS-OB-3** — Nunca registrado em log: senhas, tokens, chaves de API, cabeçalhos de autorização e todo dado das classes `credencial`, `sensível`, `financeiro` e `pessoal` (`CS-SC-6`) — CPF/CNPJ, número de cartão, endereço, e-mail e afins —, nem corpos completos de requisição ou resposta que os carreguem. Um tipo que guarda um campo protegido nunca chega a um log pelo seu `toString()`: o campo é mascarado no tipo. *Razão:* o log é copiado, retido e lido por muito mais gente que o banco. *Verificação:* teste que captura os logs dos cenários com dado protegido; teste do `toString()` mascarado.
- **CS-OB-4** — Toda integração de saída é cronometrada e contada: os clientes criados a partir dos builders auto-configurados já emitem a observação `http.client.requests` **(Spring)**, e um cliente construído à mão perde isso. Todo evento de negócio sobre o qual um envolvido perguntaria recebe uma linha `INFO` com os identificadores necessários para correlacioná-lo. Em áreas `crítica`, cada meta não funcional tem métrica e alerta, e os caminhos de erro têm contador. *Razão:* instrumentação sistemática em vez de lembrada. *Verificação:* revisão.
- **CS-OB-5** — Eventos de segurança — autenticação (sucesso e falha), autorização negada, mudança de privilégio, alteração de dado `sensível` ou `financeiro`, ação administrativa — vão para o logger dedicado `AUDIT`, separado do log operacional, em JSON com `event`, `actor`, `target`, `outcome`, `timestamp` e `traceId`, nunca com o dado protegido. Em áreas `crítica`, o destino é um armazenamento só de inclusão, com a retenção que o projeto declara. *Razão:* uma investigação precisa de uma trilha uniforme que o ruído operacional não afoga. *Verificação:* teste que confere o evento nos cenários de negação e de alteração.

## DA — Dados e transações

- **CS-DA-1** — `@Transactional` fica no método público do serviço de aplicação que implementa a porta de entrada, e em nenhum outro lugar **(Spring)**: nunca num adaptador, nunca no domínio, nunca num método privado ou autoinvocado (o proxy não o aplicará). Nenhuma chamada externa dentro de uma transação. *Razão:* transação fora do lugar falha em silêncio; chamada externa dentro dela segura conexões e mistura dois sistemas numa promessa que só um cumpre. *Verificação:* regra Semgrep ou ArchUnit para a localização da anotação; revisão.
- **CS-DA-2** — Todo consumidor de mensagem ou webhook é idempotente, com chave num identificador de negócio ou de entrega registrado antes do efeito. Trabalho agendado é idempotente. *Razão:* reentrega e repetição acontecem; o efeito não pode acontecer duas vezes. *Verificação:* teste de entrega dupla.
- **CS-DA-3** — Flyway, `V<n>__descricao_em_snake_case.sql`, ordenadas pela versão. *Razão:* uma ferramenta e uma nomenclatura, para que a ordem de aplicação seja óbvia. *Verificação:* `flyway validate` no build.
- **CS-DA-4** — Uma migração que rodou em qualquer ambiente nunca é editada. A correção é uma nova migração. *Razão:* editar uma migração aplicada faz os ambientes divergirem sem aviso. *Verificação:* `flyway validate` (checksum) no pipeline.
- **CS-DA-5** — Todas as associações `LAZY`. Open Session In View desabilitado (`spring.jpa.open-in-view=false`) **(Spring)**. Uma consulta que precisa de uma associação a declara com um join fetch ou um `@EntityGraph`. *Razão:* o OSIV esconde o N+1 atrás do carregamento lazy na camada de view. *Verificação:* teste de configuração para `open-in-view`; contagem de consultas (Hibernate Statistics) nos testes de integração dos casos de listagem.
- **CS-DA-6** — A alteração de um agregado que publica um evento usa outbox transacional: o serviço de aplicação publica pela porta de saída, e o adaptador dessa porta grava o evento numa tabela de outbox na mesma transação. Um relay o leva ao broker depois do commit — por leitura periódica da tabela ou por captura de mudanças (Debezium), onde o projeto já a opera. Nunca publicar no broker dentro da transação, nem depois do commit sem garantia. Uma integração que não cabe nesse modelo usa compensação explícita, declarada na ITS. Nenhuma transação distribuída (XA). *Razão:* gravar e publicar em dois passos sem garantia é a escrita dupla que perde ou inventa eventos. *Verificação:* revisão; teste de falha entre a gravação e a publicação.
- **CS-DA-7** — Toda raiz de agregado que pode ser alterada concorrentemente tem `@Version` (controle otimista); o conflito vira uma `BusinessException` com código estável, devolvida como HTTP 409. Lock pessimista só quando a ITS o declara, com o motivo. Saldo, contador e estoque mudam por operação atômica no banco, nunca por ler, calcular e gravar em memória. Trabalho agendado é protegido contra instâncias simultâneas (ShedLock ou equivalente). *Razão:* ler-decidir-gravar sem protocolo perde atualizações sem erro nenhum. *Verificação:* revisão; teste de conflito de versão.

## RS — Resiliência

- **CS-RS-1** — Timeouts padrão, configurados em propriedades e nunca no ponto de chamada:
  - HTTP de saída: conexão 2 s, leitura 5 s — `spring.http.clients.connect-timeout` e `spring.http.clients.read-timeout` para todos os clientes, e `spring.http.serviceclient.<grupo>.*` para o grupo que precisa de outro valor **(Boot 4)**; no Boot 3, no `*Properties` de cada cliente;
  - obtenção de conexão do pool do banco: 5 s (`spring.datasource.hikari.connection-timeout=5000`) **(Spring)**;
  - transação: 30 s (`spring.transaction.default-timeout=30s`) **(Spring)**;
  - confirmação de publicação no broker: 5 s;
  - lock distribuído: sempre com prazo de espera, nunca indefinido.

  Repetição: até 3 novas tentativas, com espera de 200 ms, 400 ms e 800 ms e variação aleatória, somente para falhas transitórias — erro de conexão, timeout, HTTP 429, 502, 503 e 504 — e somente em operação idempotente ou com chave de idempotência (`CS-DA-2`). O mecanismo é o `@Retryable` do Spring Framework 7, habilitado por `@EnableResilientMethods` **(Boot 4)**, sempre com as exceções transitórias declaradas — sem elas, ele repete qualquer exceção; no Boot 3, o Retry do Resilience4j. A ITS ou a configuração declaram outro valor quando a dependência pede. *Razão:* vários clientes HTTP da plataforma têm timeout de leitura infinito por padrão, e uma dependência lenta sem timeout esgota a capacidade de todo o resto. *Verificação:* regra Semgrep para cliente construído sem os builders auto-configurados e para `@Retryable` sem exceções declaradas; teste com servidor lento (WireMock) por cliente.
- **CS-RS-2** — Toda dependência externa não essencial passa por circuit breaker (Resilience4j) com o comportamento degradado declarado na ITS. Em áreas `crítica`, toda dependência externa tem circuit breaker e limite de concorrência — `@ConcurrencyLimit` do Spring Framework 7 **(Boot 4)**, ou o bulkhead do Resilience4j. Valores iniciais do circuit breaker: janela de 20 chamadas, abertura com 50% de falha, meia-abertura após 30 s. *Razão:* uma dependência fora do ar não pode derrubar o que não depende dela — e, com threads virtuais, nenhum pool de threads limita mais a pressão sobre ela. *Verificação:* revisão; teste com a dependência indisponível.

## CT — Contratos externos

- **CS-CT-1** — Contratos publicados:
  - **API:** versão no caminho (`/api/v1/...`), declarada pelo suporte nativo de versionamento de API do Spring Framework 7 — atributo `version` nos mapeamentos e configuração em `spring.mvc.apiversion.*` **(Boot 4)**; no Boot 3, o prefixo no mapeamento. Dentro de uma versão, apenas mudanças aditivas — campo opcional novo sim; campo removido ou renomeado, tipo estreitado ou código de erro alterado, não. Uma quebra é uma nova versão; a antiga anuncia o fim com os cabeçalhos `Deprecation` e `Sunset`.
  - **Evento:** o payload carrega a versão do esquema; consumidores ignoram campos desconhecidos; uma quebra é um novo tipo ou uma nova versão do evento.
  - **Esquema de banco:** mudanças compatíveis com a versão em produção por um release — adicione antes de usar, pare de usar antes de remover; nunca renomear ou remover uma coluna no mesmo release em que o código para de usá-la.

  *Razão:* os deploys sobrepõem versões, e consumidores fora da mudança não migram junto — entre microsserviços, cada um no seu ritmo. *Verificação:* comparação do OpenAPI entre a versão anterior e a nova no pipeline (openapi-diff ou equivalente); testes de contrato entre produtor e consumidor (Spring Cloud Contract ou Pact) para APIs e eventos consumidos por outro serviço; teste de migração aplicada sobre o esquema da versão anterior.
- **CS-CT-2** — Paginação por página com `page`/`size`; `size` padrão 20 e máximo 100, impostos no servidor (`spring.data.web.pageable.default-page-size` e `max-page-size`) **(Spring)**. Ordenação via `sort=campo,direcao`. Coleções sempre retornam um envelope com os metadados da página — `PagedModel`, com `@EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO)` **(Spring)** —, nunca um array puro nem um `Page` serializado direto. Exportações e processamentos em massa trabalham em lotes de tamanho declarado. *Razão:* uma listagem sem limite no servidor é trabalho ilimitado sobre dado que cresce, e um `Page` serializado expõe uma estrutura interna que muda entre versões. *Verificação:* teste de integração com `size` acima do máximo.
- **CS-CT-3** — DTOs de requisição e resposta são tipos `record` no adaptador de entrada, com anotações do Bean Validation; payloads de evento são `record` no adaptador de mensageria. O mapeamento para o comando da porta e a partir do modelo de domínio é explícito, feito no adaptador e testado; nenhuma entidade nem objeto de domínio é jamais serializado. *Razão:* o contrato muda quando o contrato muda, não quando a tabela muda. *Verificação:* ArchUnit para tipos de persistência na API; teste do mapeamento.
- **CS-CT-4** — `Instant` em UTC para instantes, `LocalDate` para datas sem hora, ISO-8601 no fio — o padrão do Jackson 3 **(Boot 4)**; no Jackson 2, com `WRITE_DATES_AS_TIMESTAMPS` desligado. `BigDecimal` para dinheiro, com a escala declarada e a moeda explícita quando houver mais de uma — nunca `double` ou `float`. `UUID` para identificadores externos; identificadores de sequência do banco nunca são expostos. Um identificador gerado pela aplicação é UUID versão 7 (`@UuidGenerator(style = VERSION_7)`, Hibernate 7) **(Spring)**, ordenado no tempo. *Razão:* ponto flutuante corrompe centavos e instante sem fuso corrompe horários — em silêncio; um UUID aleatório como chave espalha as inserções pelo índice. *Verificação:* revisão; regra Semgrep para `double`/`float` em campos monetários.

## TS — Testes

- **CS-TS-1** — Nunca entra em merge sem teste:
  - regra de negócio nova ou alterada — teste unitário no domínio;
  - caso de uso novo ou alterado — teste unitário do serviço de aplicação, com dublês das portas de saída;
  - adaptador de entrada novo ou alterado (endpoint, consumidor, job) — teste de integração do adaptador;
  - adaptador de saída novo ou alterado — teste de integração contra a infraestrutura real (Testcontainers) ou simulada no fio (WireMock);
  - contrato publicado novo ou alterado — teste de contrato (`CS-CT-1`);
  - bug corrigido — um teste que falha antes da correção;
  - migração de esquema — teste de integração aplicado sobre o esquema anterior.

  Todo o resto é julgamento. *Razão:* são as categorias em que a ausência de teste vira incidente. *Verificação:* revisão.
- **CS-TS-2** — `*Test` para testes unitários (sem contexto Spring), `*IT` para testes de integração (Testcontainers, banco real, ligados à aplicação por `@ServiceConnection` **(Spring)**). Os nomes dos métodos declaram cenário e expectativa: `should_rejectOrder_when_creditLimitExceeded`. JUnit Jupiter na versão que o Spring Boot gerencia — JUnit 6 no Boot 4 — e AssertJ. Teste de controller com `MockMvcTester`; teste de integração HTTP com `RestTestClient` **(Boot 4)**, não com o `TestRestTemplate`. Suporte a JUnit 4 (Vintage, `SpringRunner`) não entra em código novo — está descontinuado no Spring Framework 7. *Razão:* o nome do teste que falha já diz o que quebrou, e as asserções fluentes dizem por quê. *Verificação:* configuração do Surefire e do Failsafe; regra de nomenclatura no Checkstyle.
- **CS-TS-3** — Dublê apenas nas fronteiras, e o hexágono diz onde elas estão. No teste do serviço de aplicação, as portas de saída — de preferência um fake em memória, que guarda estado, a um mock que só confere chamadas. No teste do adaptador de saída, o que está do outro lado do fio: HTTP de outro serviço (WireMock), broker; o banco é real via Testcontainers. O relógio é sempre injetado. Num contexto Spring, `@MockitoBean` e `@MockitoSpyBean` — o `@MockBean` e o `@SpyBean` do Boot foram removidos no Boot 4. Nunca um dublê do tipo sob teste, do domínio nem de seus value objects. *Razão:* a porta é a fronteira que o núcleo enxerga, e um banco em memória testa um dialeto que ninguém roda em produção. *Verificação:* revisão.
- **CS-TS-4** — Sem `Thread.sleep` para sincronização; use Awaitility. Sem dependência da ordem de execução, sem estado compartilhado entre testes, sem `LocalDateTime.now()` direto — o tempo é injetado por um `Clock`. *Razão:* uma suíte ocasionalmente vermelha ensina o time a ignorar o vermelho. *Verificação:* regra Semgrep para `Thread.sleep` e `now()` sem `Clock` nos testes; ordem aleatória no Surefire (`runOrder=random`); detecção de testes instáveis no CI.
- **CS-TS-5** — Um teste sai da suíte só com `@Disabled("ITEM-123: motivo")`, com o item do tracker que o traz de volta e cujo responsável responde pelo teste. Nunca comentar o teste, nunca `assumeTrue(false)`, nunca apagá-lo para ficar verde. Uma asserção existente alterada ou removida aponta, na descrição do PR, o item da ITS que mudou aquele comportamento. *Razão:* o teste desativado sem caminho de volta e a asserção afrouxada em silêncio são as duas formas de a suíte deixar de proteger. *Verificação:* regra no pipeline que falha em `@Disabled` sem item e sinaliza no diff asserção removida ou teste apagado.

## SC — Segurança

- **CS-SC-1** — A autorização é imposta no serviço de aplicação, em nível de método (`@PreAuthorize` com `@EnableMethodSecurity`, ou verificação explícita) **(Spring)**. A configuração de segurança, no DSL de lambdas do Spring Security 7, nega por padrão: toda rota não declarada é negada (`anyRequest().denyAll()` depois das regras explícitas). Uma operação sobre um recurso por identificador verifica que o recurso pertence ao chamador — com a consulta já restrita ao titular, nunca filtrando depois de carregar. Erro na decisão de autorização nega. Uma verificação feita só no controller é insuficiente; uma verificação feita só no cliente não é uma verificação. *Razão:* controle de acesso quebrado é o risco número um da OWASP, e a forma mais comum é o acesso a recurso alheio por identificador. *Verificação:* testes de autorização negativa por endpoint novo — sem permissão e sobre recurso de outro titular; revisão.
- **CS-SC-2** — Bean Validation em todo DTO de fronteira, com semântica de allowlist. Consultas parametrizadas — nunca concatenação em JPQL, SQL nativo ou Criteria. A entrada externa nunca chega a um caminho de arquivo, a um comando ou a um desserializador sem neutralização. Saída codificada pelo contexto: templates com escape automático; valores em log só por parâmetro do SLF4J, sem quebras de linha vindas da entrada. *Razão:* quase toda injeção é dado que cruzou para código sem ser neutralizado. *Verificação:* Semgrep, SpotBugs com find-sec-bugs, SAST no pipeline.
- **CS-SC-3** — Nenhuma credencial em `application.yml`, em arquivo de propriedades, em fixture de teste ou no controle de versão. Resolvidas do cofre do projeto (Spring Cloud Vault ou o gerenciador de segredos da nuvem) ou, no Kubernetes, montadas como arquivos e importadas por `spring.config.import=configtree:` **(Spring)**; rotacionáveis sem rebuild. *Razão:* o histórico do Git é permanente. *Verificação:* gitleaks no pre-commit e no pipeline.
- **CS-SC-4** — Senha nova com Argon2id nos parâmetros mínimos da OWASP — 19 MiB de memória, 2 iterações, paralelismo 1: `new Argon2PasswordEncoder(16, 32, 1, 19456, 2)` —, registrado num `DelegatingPasswordEncoder` com o identificador `argon2` **(Spring)**. Hashes bcrypt existentes continuam válidos pelo mesmo encoder e são regravados em Argon2id no login (`UserDetailsPasswordService`). Tokens JWT são validados pelo OAuth2 Resource Server do Spring Security e emitidos pelo provedor de identidade do projeto ou pelo Spring Authorization Server **(Spring)** — nunca montados nem conferidos à mão. Nenhum algoritmo artesanal, nenhum `MessageDigest` como hash de senha, nenhum `Random` onde `SecureRandom` é exigido. *Razão:* criptografia própria falha de formas que nenhum teste funcional mostra, e um parâmetro fraco de hash só aparece no dia do vazamento. *Verificação:* SpotBugs com find-sec-bugs; regra Semgrep.
- **CS-SC-5** — OWASP ASVS 5.0 Nível 2 como conjunto de controles de referência; Nível 3 nas áreas `crítica` quando o modelo de ameaças do projeto o pede. *Razão:* um padrão externo mantido por especialistas em vez de uma lista reescrita e envelhecida. *Verificação:* revisão contra os controles aplicáveis.
- **CS-SC-6** — Quatro classes de dado protegido:
  - `credencial` — senha, token, chave;
  - `sensível` — dado pessoal sensível conforme a LGPD (art. 5º, II): saúde, biometria, origem racial ou étnica e afins;
  - `financeiro` — número de cartão, conta, saldo;
  - `pessoal` — o que identifica alguém: nome, CPF, e-mail, telefone, endereço.

  O campo usa um tipo de valor da classe (`Cpf`, `Email`, `NumeroCartao`) com `toString()` mascarado. `credencial` nunca é registrada, retornada ou guardada em claro. `sensível` e `financeiro` são mascarados em toda resposta que não precise do valor completo, e seu acesso é auditado (`CS-OB-5`) nas áreas `crítica`. `pessoal` fica fora dos logs e é exposto só onde a finalidade pede. A retenção de cada classe é declarada pelo projeto. *Razão:* sem classificação, cada dev decide sozinho o que é sensível — e decide diferente. *Verificação:* revisão; teste do `toString()` mascarado.

## DP — Dependências de terceiros

- **CS-DP-1** — Uma nova dependência declara o problema que resolve, por que a plataforma ou uma dependência existente não o resolve, sua atividade de releases e sua licença. As coordenadas são copiadas da página oficial do projeto e conferidas no Maven Central — nunca digitadas de memória. A versão é fixa: sem faixas, sem `LATEST`/`RELEASE`, sem SNAPSHOT em artefato entregue; quando o Spring Boot gerencia a dependência, vale a versão dele. Aprovada pelo arquiteto. *Razão:* geradores de código inventam nomes de pacote plausíveis, e versão dinâmica muda o artefato sem mudar o código. *Verificação:* Maven Enforcer (`banDynamicVersions`); revisão da admissão.
- **CS-DP-2** — Uma biblioteca por preocupação:
  - tempo: `java.time`;
  - JSON: Jackson — o Jackson 3 (`tools.jackson`) no Boot 4; a passagem do Jackson 2 para o 3 é uma migração declarada, nunca uma convivência sem prazo;
  - logging: SLF4J;
  - HTTP de saída: `RestClient` e os clientes de serviço HTTP do Spring; o `RestTemplate` não entra em código novo — está descontinuado a partir do Spring Framework 7.1;
  - infraestrutura de teste de integração: Testcontainers;
  - resiliência: o suporte nativo do Spring Framework 7 para repetição e limite de concorrência **(Boot 4)**, e o Resilience4j para circuit breaker — e também para repetição no Boot 3.

  Joda-Time, Gson, `java.util.Date` e o tratamento de datas do Apache Commons não são introduzidos. *Razão:* é assim que uma base acaba com três bibliotecas de data. *Verificação:* Maven Enforcer (dependências banidas).
- **CS-DP-3** — Nenhum release sai com um alerta alto ou crítico aberto. O Renovate mantém as versões andando; a varredura roda no pipeline. O build gera o SBOM CycloneDX (`cyclonedx-maven-plugin`, com a versão gerenciada pelo Spring Boot), empacotado no artefato **(Spring)**. Uma exceção segue o registro de exceção do `quality-model` — com prazo e responsável —, nunca um comentário de supressão que ninguém revisita. *Razão:* a localização de uma dependência vulnerável é pública, e sem SBOM ninguém responde rápido "onde usamos isto?". *Verificação:* varredura de dependências e geração do SBOM no pipeline.

## EV — Evolução e dívida

- **CS-EV-1** — Flags via propriedade `feature.<area>.<nome>` lida por `@ConditionalOnProperty` **(Spring)** quando a flag só muda num novo deploy; pelo serviço de flags do projeto, atrás da API OpenFeature, quando ela muda sem reinício. Desligadas por padrão. Toda flag nasce com a condição de remoção (data ou evento) num item do tracker, citado num comentário na declaração. Uma flag com a condição vencida é dívida a pagar (`QM-MT-1`). *Razão:* flag sem data de remoção vira ramo permanente que ninguém testa. *Verificação:* revisão; busca por flags com condição vencida.
- **CS-EV-2** — Dívida no código é marcada `// TODO(ITEM-123): motivo`, sempre com o item do tracker; `FIXME` e `XXX` não são usados. O responsável é o do item. *Razão:* um marcador sem item nunca entra numa priorização. *Verificação:* Checkstyle `TodoComment` com formato que exige o item, ou regra Semgrep.

## PR — Soluções canônicas e proibições

- **CS-PR-1** — O registro cresce por projeto no `docs/prime-config.md`, cada entrada com seu exemplo canônico. Entradas válidas para o time todo:
  - chamada a outro serviço: um adaptador `*Client` em `adapter.out.http` que implementa a porta de saída sobre uma interface de cliente de serviço HTTP (`@HttpExchange`), registrada com `@ImportHttpServices` e configurada por grupo **(Boot 4)** — no Boot 3, sobre o `RestClient` —, com os valores de `CS-RS-1` e `CS-RS-2` e a tradução de erro de `CS-ER-3`;
  - consumo de mensagem: um adaptador `*Listener` em `adapter.in.messaging` que desserializa, confere a idempotência (`CS-DA-2`) e chama a porta de entrada;
  - trabalho agendado: um adaptador `*Job` que chama a porta de entrada, conforme `CS-DA-2` e `CS-DA-7`;
  - evento publicado conforme `CS-DA-6`.

  *Razão:* um problema recorrente resolvido de um jeito só. *Verificação:* revisão.
- **CS-PR-2** — Proibidos, cada um com sua razão:
  - **Injeção por campo** (`@Autowired` num campo) — esconde dependências e torna o tipo intestável sem um container (`QM-TS-3`). Somente injeção por construtor.
  - **`catch (Exception e)`** fora do advice de fronteira — captura o que não antecipou e transforma um defeito em silêncio (`QM-EO-1`).
  - **Estado mutável estático** — o acoplamento invisível que o `QM-CC-1` nomeia como o pior tipo.
  - **Lombok `@Data` em entidades** — gera `equals`/`hashCode` sobre campos mutáveis e carregados de forma lazy, produzindo corrupção de coleções que aflora longe da causa (`QM-RC-1`).
  - **Entidade como `@RequestBody`** — faz do modelo de persistência o contrato público e abre mass assignment (`QM-SR-1`).
  - **Lógica de negócio em trigger de banco ou stored procedure** — invisível para o código, intestável na suíte, sem versionamento junto com a mudança (`QM-CC-6`).
  - **Thread ou executor criado sem ciclo de vida gerenciado** (`new Thread`, `Executors.new*` fora de um bean com encerramento) — vaza recursos e sobrevive ao contexto (`QM-RB-2`).
  - **Desserialização nativa do Java** (`ObjectInputStream`) de dado externo — execução de código a partir da entrada (`QM-SR-1`).
  - **Cliente HTTP construído à mão** (`new RestTemplate()`, `RestClient.create()`, `HttpClient.newHttpClient()` no ponto de chamada) — escapa dos timeouts e da observação configurados para todos (`QM-RB-1`, `QM-EO-7`).
  - **Adaptador injetado no núcleo** — um `*Repository` do Spring Data, um `*Client` ou um `*Publisher` usado direto por um serviço de aplicação, em vez da porta de saída — amarra o caso de uso à tecnologia e impede testá-lo sem ela (`QM-CC-3`).

  *Verificação:* Error Prone, SpotBugs, Semgrep, ArchUnit.

## Toolchain do time

As ferramentas que as verificações acima nomeiam. Um projeto que não tem uma delas tem uma lacuna de toolchain a registrar — não um slot a revisar à mão.

- **Build:** Spotless com um formatador de Java (google-java-format ou palantir-java-format) · ArchUnit, com a regra de arquitetura hexagonal e as regras de nomenclatura e de import · Error Prone com NullAway em modo JSpecify · SpotBugs com find-sec-bugs · Checkstyle · Maven Enforcer (`banDynamicVersions` e dependências banidas) · `flyway validate` · CycloneDX para o SBOM.
- **Regras do time:** Semgrep. Vários slots que parecem regras em prosa ("nunca chame um repositório a partir de um controller", "nunca concatene em JPQL", "cliente HTTP sem os builders auto-configurados", "`@Retryable` sem exceções declaradas") são expressáveis como regras customizadas, o que os tira da revisão e os coloca no build.
- **Testes:** JUnit Jupiter (JUnit 6 no Boot 4) · AssertJ · `MockMvcTester` · `RestTestClient` · Testcontainers com `@ServiceConnection` · WireMock · Spring Cloud Contract ou Pact para os contratos entre serviços · Awaitility · Hibernate Statistics para contagem de consultas · PIT para teste de mutação nas áreas `crítica`.
- **Pipeline:** gitleaks · varredura de dependências · Renovate · comparação de OpenAPI · detecção de testes instáveis · regra de `@Disabled` sem item.
- **Migrações mecânicas:** receitas do OpenRewrite (subida de Spring Boot, Jackson 2 → 3, JUnit, anotações de teste), executadas em bloco conforme as migrações declaradas.
